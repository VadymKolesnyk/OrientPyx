# План: спільна робота кількох станцій над одним змаганням («Мережевий режим»)

Статус: **реалізовано** (етапи 1–5, 2026-11-05; протокол — `docs/network-protocol.md`, межа в коді описана в
`CLAUDE.md` «Network mode»). Дата плану: 2026-11-04 (уточнено 2026-11-05 після перевірки коду, див.
`docs/network-mode-implementation.md` §0).

## 1. Мета

Два (або кілька) комп'ютери з OrientPyx працюють **одночасно** над однією базою змагання по локальній мережі:
один стає **хостом** (у нього лежить `events/<id>/event.db`, він єдиний її відкриває), інші — **станціями**
(клієнтами), які бачать той самий інтерфейс і редагують ті самі дані наживо. Типовий сценарій: основний
комп на Windows біля зчитки чіпів і принтера, допоміжний Mac на реєстрації/видачі чіпів/стартовому
протоколі.

Головна вимога — **підключення без ручних налаштувань на місці**: без інтернету, без введення IP, без
правок брандмауера руками; усе, чого бракує, програма сама знаходить і пропонує виправити однією кнопкою.

### Не-цілі

- Робота через інтернет / хмару (лише локальна мережа; онлайн-результати лишаються окремою фічею).
- Автономне редагування на станції без зв'язку з наступним злиттям (при обриві станція працює лише в режимі
  перегляду останнього знімка).
- Повноцінні облікові записи й права доступу — лише PIN підключення; усі станції рівноправні.
- Понад ~5 станцій одночасно; оптимізація під великі навантаження.

## 2. Від чого відштовхуємося

- **Увесь доступ до бази змагання йде через один інтерфейс** `IEventStore` (BusinessLogic/Interfaces, 129
  асинхронних методів, перевантажень немає). Кожен метод приймає `eventFolderPath`; по мережі замість шляху
  передається **ідентифікатор змагання** (§3, «Ключ змагання»). Моделі — прості POCO/records (сутності,
  `EventDaySnapshot`, налаштування), словники лише з ключами `Guid`/`int`/`string` (System.Text.Json їх
  підтримує). Винятки, які не серіалізуються: `IProgress<ImportProgress>` в імпорті, `CancellationToken` (не
  передаємо, рветься разом із запитом), `ReleaseAsync`/`CheckpointAsync` (файлові операції хоста), три методи
  з кортежами `(Guid, …)` (потрібен `IncludeFields`).
- Решта інфраструктури DataAccess поділяється на **прив'язану до папки змагання** (`IEventFolderScanner`,
  `IEventCatalogService`, `IEventArchiveService` — zip `events/<id>`, архів імпортованих XML у `events/<id>/day{N}`,
  `views.json`) і **локальну для машини** (`IAppStore`/`app.db`, `IActivityLog`, `IPluginCatalog`, друк, запис
  DOCX/HTML, зчитка).
- **Частина даних для результатів лежить в `app.db`**: правила очок, перелік розрядів, таблиця кваліфікації
  й умови розрядів (`CompetitionEditorService.LoadDayResultsAppDataAsync` → `IAppStore`). На станції вони
  **мають братися з хоста**, інакше дві машини порахують різні очки/розряди (§3, «Дані з app.db хоста»).
- `ISessionService` тримає активне змагання/день у пам'яті та має подію `SessionChanged`. Її обробляє
  `MainWindowViewModel` (оновлює доступність команд); кожна сторінка підписується і перезавантажується
  по-своєму — спільного хука «перезавантажити сторінку» в `PageViewModelBase` поки немає, він з'являється в
  етапі 1.
- Файлові операції повз `IEventStore` є у BusinessLogic (`CompetitionEditorService`: папки днів, архів XML,
  шляхи HTML монітора; `EventCatalogService`: створення/перейменування папки) і в Presentation (дефолтні шляхи
  файлів зчитки будуються з `FolderPath`). Усі вони на станції мають або йти на хост, або бути локальними (§3).
- Кілька екземплярів над одним `./data` на одній машині вже допускаються; конфлікти вирішуються «останній
  запис виграє по клітинці». Мережевий режим зберігає це правило.
- SQLite через SMB/синхронізатори відкинуто (WAL не працює на мережевих ФС, блокування ненадійне); окремий сервер
  БД відкинуто через складність налаштування на місці.

## 3. Архітектурні рішення

| Питання | Рішення | Чому |
|---|---|---|
| Де межа «мережі» | На рівні `IEventStore` + `IEventFolderScanner`, `IEventCatalogService`, `IEventArchiveService`, нового `IEventFiles` (файли папки змагання) і нового `IResultsAppData` (таблиці очок/розрядів): станція отримує **проксі-реалізації**, усе вище (редактор, калькулятор, сторінки) не змінюється | Вузькі інтерфейси, уже з ключем змагання; бізнес-логіка однакова на обох ролях |
| Як робити проксі на 129 методів | **Автоматично**: `System.Reflection.DispatchProxy` + `System.Text.Json`: `POST /rpc/{Interface}/{Method}` з масивом аргументів, відповідь — результат. Хост викликає той самий метод на зареєстрованому в DI `IEventStore` (зовнішньому декораторі, щоб спрацювали події) рефлексією по імені | Жодного ручного дублювання; новий метод у `IEventStore` працює по мережі «сам» (під контролем тесту, §9) |
| JSON-RPC чи gRPC | **JSON по HTTP/1.1** (DispatchProxy + System.Text.Json), не gRPC | gRPC вимагає `.proto` або code-first-анотацій (`protobuf-net.Grpc`) на всіх ~130 методах і всіх моделях BusinessLogic (Guid, DateTimeOffset, TimeSpan, records — через обгортки), тобто втрачається автоматична генерація проксі й з'являється зв'язність шару моделей із транспортом. Переваги gRPC (бінарний розмір, потоки, строгий контракт) на 2–5 станцій у LAN не відчутні: мандатка на 600 рядків — сотні КБ JSON за десятки мс. JSON можна читати очима й перевіряти `curl`, а в майбутньому віддати браузеру. Для користувача різниці в налаштуванні немає (один TCP-порт в обох випадках). Повернутися до gRPC має сенс лише якщо з'явиться потік великих даних |
| HTTP-сервер | **Kestrel** через `<FrameworkReference Include="Microsoft.AspNetCore.App">` у DataAccess (мінімальний API без MVC; `WebApplication.CreateEmptyBuilder` + `UseKestrelCore`, щоб не підхоплювати `appsettings.json`/`ASPNETCORE_*`) | `HttpListener` на Windows вимагає URL ACL (`netsh http add urlacl`) або адмін-прав для не-loopback адрес — це саме «налаштування руками», якого треба уникнути. Kestrel слухає сокет напряму: потрібен лише дозвіл брандмауера. Ціна — ~30 МБ у self-contained збірці |
| Де живе код | Контракти й стани — `BusinessLogic/Interfaces` (`IWorkspaceMode`, `IDataChangeBus`, `IEventFiles`, `IResultsAppData`, `INetworkHost`, `INetworkClient`, `IStationDiagnostics`); `NotifyingEventStore` — BusinessLogic; **маршрутизатори, хост, клієнтські проксі, пошук, діагностика — `DataAccess/Network/`**; UI — сторінка «Спільна робота» в Presentation | Маршрутизатор тримає і локальний `EventStore`, і `RemoteEventStore` — обидва класи DataAccess, тож BusinessLogic його мати не може (напрямок залежностей). Мережа — інфраструктура, без знань про UI |
| Перемикання ролі без перезапуску | Ланцюг у DI: `IEventStore` = `NotifyingEventStore( RoutingEventStore( EventStore \| RemoteEventStore ) )`; так само `Routing*` для сканера, каталогу, архіву, файлів, `IResultsAppData`. Маршрутизатор дивиться на `IWorkspaceMode.Role` при кожному виклику | Усі сервіси — singleton із конструкторним впровадженням; підміна реалізації на льоту можлива тільки через маршрутизатор. Хост-диспетчер викликає зовнішній `IEventStore`, тому правки станцій теж публікують події |
| Ключ змагання по мережі | По мережі ходить **ідентифікатор** (назва папки), не шлях: на станції `EventSummary.FolderPath` = ідентифікатор з хоста; хост-диспетчер перекладає параметр `eventFolderPath` і `EventSummary.FolderPath` у вхідних аргументах на `events/<identifier>` (валідація: `EventIdentifier.IsValid`, без роздільників), а у відповідях — назад на ідентифікатор | Інакше станція з токеном могла б змусити хост створити папку/базу за довільним шляхом (`EnsureCreatedAsync` робить `Directory.CreateDirectory`). Для коду станції рядок лишається непрозорим ключем |
| Сповіщення про зміни | Лічильник версії даних на змагання: кожен запис через `IEventStore` інкрементує версію і публікує `DataChange(eventPath, area, version, origin)` в `IDataChangeBus`. Хост транслює це станціям по **Server-Sent Events** (`GET /changes`, `id:` — глобальний монотонний номер події, версія змагання в тілі), станції — у свій локальний `IDataChangeBus`. На станції `NotifyingEventStore` **не публікує** (події приходять лише з SSE); `origin` = ім'я станції або хоста, активна сторінка ігнорує події зі своїм власним `origin` (вона вже оновилась сама) | Одна шина і для хоста, і для станцій: сторінки хоста теж бачать правки станцій. SSE простіший за WebSocket і проходить крізь будь-який проксі/брандмауер як звичайний HTTP |
| Дані з app.db хоста | `IResultsAppData` (правила очок, розряди, кваліфікація, умови) — локально читає `IAppStore`, на станції проксі на хост; `LoadDayResultsAppDataAsync` ходить лише через нього. Сторінки «Очки» та «Розряди» на станції — лише перегляд із банером «Редагується на хості». Зміна цих таблиць на хості публікує `DataArea.AppData` | Результати, очки й розряди на станції збігаються з хостом гарантовано, а не «якщо оператор синхронізував таблиці» |
| Автентифікація | PIN із 6 цифр на екрані хоста → `POST /pair` → токен сесії станції (`Authorization: Bearer`) | Захист від випадкового підключення чужого ноутбука в залі; без облікових записів |
| Шифрування | Відкритий HTTP у локальній мережі (перша версія) | TLS із самопідписаним сертифікатом додає кроки довіри на обох машинах; дані змагання не секретні. Залишено як можливе розширення |
| Пошук хоста | UDP-broadcast (порт `47831`) на subnet-broadcast **кожного** IPv4-інтерфейсу: станція шле `OPYX?`, хост відповідає `{name, version, ip[], port, competition}`. Лише IPv4 (Kestrel слухає `IPAddress.Any`) | Працює без mDNS/Bonjour-залежностей на обох ОС; `255.255.255.255` у Windows іде лише через один інтерфейс, а хот-спот + Wi-Fi одночасно — звичайна ситуація. Якщо broadcast заблоковано — запасний «код підключення» (§8). На macOS 14+ потрібен дозвіл «Локальна мережа» (§8.3) |
| Конфлікти | «Останній запис виграє» по клітинці; видалений іншою станцією рядок → помилка `NotFound` → тост + оновлення сторінки | Так само, як сьогодні між двома екземплярами на одній машині |
| Що лишається локальним | `app.db` (налаштування машини, API-ключі онлайну, тип відмітки), `views.json` станції (вигляд таблиць, ключ — `<hostId>/<identifier>`), лог дій (із дублюванням дій на хост із назвою станції), плагіни (мають бути встановлені й увімкнені на обох; перевіряється при підключенні), **шляхи до файлів зчитки** (дефолтні й збережені — машинні, бо файл лежить там, де підключено зчитувач), HTML монітора (табло підключене до машини оператора) | Налаштування машини не повинні «переїжджати»; вигляд таблиць — особиста річ оператора |
| Обладнання | Зчитка і друк — там, де підключено залізо; обидва йдуть через `ICompetitionEditorService` → `IEventStore`, тож працюють і на станції | Нічого не змінюється: станція біля зчитувача може читати чіпи у базу хоста |

## 4. Протокол (стисло)

```
POST /pair                        {pin, stationName, appVersion, protocolVersion, plugins[]}
                                  → {token, hostId, hostName, appVersion, protocolVersion, plugins[], serverTimeUtc}
POST /rpc/{Interface}/{Method}    Authorization: Bearer <token>; Idempotency-Key: <guid> (записи)
                                  body: [arg0, arg1, …] → result | 204 | {type, message, kind}
                                  Interface ∈ EventStore | FolderScanner | Catalog | EventFiles | Archive | AppData
GET  /changes                     SSE: id: <seq>  event: change  data: {"eventPath","area","version","origin"}
                                  (+ heartbeat «: hb» кожні 10 с; Last-Event-ID → досилання або event: full-refresh)
GET  /version?event=<identifier>  {version} — дешевий другий детектор розсинхрону
GET  /jobs/{id}                   прогрес довгих операцій (імпорт): {stage, current, total, finished, result, error}
GET  /files/archive?identifier=   завантажити .opyx, зібраний хостом;  POST /files/import → завантажити .opyx на хост
POST /log                         батч рядків логу дій станції → дописуються в лог змагання на хості з іменем станції
GET  /ping                        {hostId, hostName, appVersion, protocolVersion, time} — без токена, для діагностики
UDP 47831                         "OPYX?" → "OPYX {json}" — пошук хостів у мережі
```

Серіалізація: `System.Text.Json` із одним спільним `JsonSerializerOptions` (`IncludeFields` для кортежів,
конвертер `DisciplineId`, enum як рядки; `TimeSpan`/`DateTimeOffset` як є). Помилки хоста повертаються як
`{type, message, kind}` і на станції перетворюються на ті ж винятки, що кидає локальний код (`ArgumentException`,
`InvalidOperationException`, `KeyNotFoundException`, `OperationCanceledException`; інше → `RemoteCallException`).
`protocolVersion` — ціле число, інкрементується при будь-якій зміні сигнатур; розбіжність → відмова `/pair`.

Довгі операції з прогресом (`ImportParticipantsBatchAsync` з `IProgress`): проксі замінює `IProgress` на `jobId`,
хост виконує у фоні й публікує прогрес, станція опитує `/jobs/{id}` і передає в локальний `IProgress`. Інших
несеріалізовних параметрів у `IEventStore` немає (перевіряється тестом, §9).

### 4.1. Порти

Номери `47831` (UDP, пошук) і `47832` (TCP, API, типовий) **довільні**, їхня вимога — не бути ніким зайнятими:
не нижче 1024 (інакше потрібні права адміністратора), не з діапазону ефемерних портів Windows/macOS
(49152–65535, інакше рано чи пізно його займе чиєсь вихідне з'єднання), не зі «популярних» (5000, 8000, 8080,
3000 — зайняті dev-серверами, принт-службами, роутерами) і не зареєстровані в IANA. Важливий по-справжньому лише
**UDP-порт пошуку** — він має бути однаковим на всіх станціях. TCP-порт хост обирає так: типовий, якщо вільний,
інакше наступний вільний, і повідомляє його у відповіді на пошук та у коді підключення — для користувача номер
не існує.

### 4.2. Стійкість до обривів

Принцип: **коректність не залежить від доставки подій**. SSE лише прискорює оновлення; джерело істини — запит
до хоста після перепідключення.

- **Виявлення обриву.** Хост шле heartbeat у `/changes` кожні 10 с; станція, не отримавши нічого 30 с, вважає
  з'єднання мертвим (ловить і «напіввідкриті» TCP, коли Wi-Fi зник без FIN). Паралельно кожні 15 с станція
  робить дешевий `GET /version` — другий незалежний детектор.
- **Перепідключення.** Експоненційна пауза 1 → 2 → 5 → 10 с, без межі спроб. При відновленні станція передає
  `Last-Event-ID` = номер останньої отриманої події; хост тримає кільцевий буфер останніх подій і або досилає
  пропущені, або (якщо станція відстала далі буфера) надсилає подію `full-refresh`. Незалежно від цього
  **кожна активна сторінка перезавантажується після перепідключення** — так пропуск подій не може лишити
  застарілі дані на екрані.
- **Таймаути й повтори RPC.** Таймаут залежить від категорії методу: читання — 10 с, записи — 60 с (масові
  `Set…BatchAsync`, `DeleteAll…` на слабкому хості довші за 10 с), завдання через `/jobs` — без таймаута (опитування).
  Читання — ідемпотентні, повторюються автоматично (3 спроби, пауза 0.5/1/2 с). Записи **не повторюються
  наосліп**: клієнт додає до кожного запису заголовок `Idempotency-Key` (GUID); хост зберігає результат
  виконаного ключа ~10 хв і на повтор повертає збережену відповідь, не виконуючи метод знову. Тож «мережа зникла
  після того, як хост записав, але до того, як станція отримала відповідь» не дає дубльованого учасника чи двічі
  присвоєного чіпа. З цим і записи можна повторювати тими ж правилами.
- **Довгі операції** (імпорт) — через `/jobs/{id}`; обрив під час імпорту не зупиняє його на хості, станція
  після відновлення просто опитує той самий `jobId`.
- **Поведінка UI.** Банер «Немає зв'язку з хостом» блокує редагування, але сторінка лишається видимою з останнім
  знімком; значення, що редагувалось у клітинці на момент обриву, зберігається і відправляється після
  відновлення (або підсвічується червоним, якщо запис остаточно не вдався, і його можна скопіювати).
- **Перезапуск хоста.** Токени станцій зберігаються на хості в `app.db`, тож після перезапуску програми-хоста
  станції перепідключаються без повторного PIN. PIN потрібен лише при першому спарюванні або після «Відключити
  всі станції».
- **Перезапуск станції.** Остання адреса хоста і токен збережені локально; станція стартує одразу в режимі
  підключення. Покажчик останнього сеансу (`LastSessionRow`) зберігає **режим і `hostId`**: сеанс станції
  відновлюється лише після успішного підключення до того самого хоста, а якщо хост недоступний — показується
  екран «Підключитися» із запам'ятованим хостом. Локально такий покажчик **ніколи не відновлюється** (інакше
  `EnsureCreatedAsync` створила б на станції порожнє змагання з іменем чужого).

### 8.1. Пошук хоста

- UDP-broadcast `47831` на subnet-broadcast кожного IPv4-інтерфейсу з відповіддю хоста; станція показує список
  «OrientPyx на `Головний-ноут` · Кубок міста · v0.8.0». Повтор кожні 2 с, доки не підключились.
- Запасний **код підключення**: хост показує IP:порт і стислий код (12 символів Base32 без 0/O/1/I = IP + порт),
  який можна продиктувати через залу і ввести на станції, якщо broadcast не пройшов (ізоляція клієнтів у
  гостьовому Wi-Fi — часта ситуація в спортзалах і школах).
- Станція запам'ятовує останній хост і **перепідключається сама** після обриву (етап 3).

### 8.2. Самоперевірка на хості при вмиканні ролі (`IStationDiagnostics`)

Кожна перевірка — рядок зі статусом ✓/✗, поясненням і кнопкою «Виправити», де це можливо:

| Перевірка | Як | Виправлення однією кнопкою |
|---|---|---|
| Є локальна мережа | IPv4 на не-loopback інтерфейсі, не APIPA (169.254.x.x) | Windows: відкрити «Мобільний хот-спот» (`ms-settings:network-mobilehotspot`) із порадою «увімкніть, підключіть Mac до цієї мережі». macOS: відкрити Системні налаштування → Wi-Fi |
| Порт вільний | спроба `bind` | Автоматично взяти наступний вільний порт (нічого натискати) |
| Брандмауер Windows пропускає вхідні | правило `OrientPyx` існує (COM `HNetCfg.FwPolicy2`, без прав; запасний шлях `netsh advfirewall firewall show rule name=OrientPyx`) | Додати правило для поточного exe (`netsh advfirewall firewall add rule … program=<exe> action=allow profile=any`) через запуск із підвищенням прав (UAC — один клік «Так»). Запасний шлях — стандартний запит Windows «Дозволити доступ» при першому старті сервера |
| Профіль мережі «Публічний» | `Get-NetConnectionProfile` | **Лише порада**, без кнопки: правило з `profile=any` діє в будь-якому профілі (§8.2.1). Показується як пояснення, чому міг не з'явитися стандартний запит Windows |
| Брандмауер macOS | `/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate` | Пояснення + відкриття панелі; система сама запитає «дозволити вхідні?» при першому слуханні. Застереження: для непідписаного `.app` macOS може питати при кожному запуску |
| Порт справді доступний зовні | хост сам підключається до себе **через LAN-IP** (не loopback) і викликає `/ping` | Якщо не вдалось — показує, яка з попередніх перевірок найімовірніше винна |

Якщо все зелене — показує один великий екран: «Готово. На іншому комп'ютері оберіть „Підключитися“ → `Головний-ноут`, PIN **482 913**».

### 8.2.1. Як саме програма змінює налаштування системи

Правила: програма **нічого не змінює мовчки** — кожна зміна показана у списку перевірок із поясненням і
виконується лише натисканням «Виправити»; усі зміни — виключно «дозволити цій програмі вхідні з'єднання»;
кожна записується у лог дій і має зворотну кнопку («Прибрати правило»).

**Windows.**
- Основний шлях — узагалі без наших змін: коли Kestrel уперше починає слухати на не-loopback адресі, Windows
  Defender Firewall сам показує стандартне вікно «Дозволити цьому застосунку обмін даними в мережах» і створює
  правило для exe. Шлях exe встановленої збірки стабільний між оновленнями (`%LocalAppData%\OrientPyx\current\
  OrientPyx.exe` — Velopack перейменовує нову версію в `current`; packId `OrientPyx`), тож правило переживає
  оновлення.
- Коли цього не сталося (користувач натиснув «Скасувати», вікно вимкнене політикою, або мережа «Публічна» і
  правило створилося тільки для приватних): перевірка «Порт доступний зовні» (самопідключення через LAN-IP)
  червона → кнопка «Додати правило брандмауера». Вона запускає підвищений процес (`ProcessStartInfo { Verb =
  "runas", UseShellExecute = true }`, один запит UAC) із командою
  `netsh advfirewall firewall add rule name="OrientPyx" dir=in action=allow protocol=TCP program="<exe>" profile=any`
  і такою ж для UDP-порту пошуку. **`profile=any` робить зміну профілю мережі з «Публічного» на «Приватний»
  непотрібною** — правило діє в будь-якому профілі; тому «Профіль мережі» в таблиці §8.2 — порада, а не крок.
  Наявність правила перевіряється без прав адміністратора через COM (`HNetCfg.FwPolicy2`) або `netsh … show rule`.
- Хот-спот програма **не вмикає сама** (WinRT `NetworkOperatorTetheringManager` ненадійний і потребує адаптера з
  підтримкою) — лише відкриває потрібну сторінку налаштувань (`ms-settings:network-mobilehotspot`).
- Видалення: кнопка «Прибрати правило» (`netsh … delete rule name="OrientPyx"`, UAC) і best-effort у Velopack-хуку
  `OnBeforeUninstall` (без прав адміністратора не вдасться — лишиться правило-дозвіл для вже неіснуючого exe, що
  безпечно).

**macOS.**
- Нічого на кшталт URL ACL немає. Якщо системний брандмауер вимкнений (типово для більшості Mac) — робити нічого
  не треба. Якщо ввімкнений — при першому слуханні macOS сам питає «Дозволити вхідні з'єднання?»; відповідь
  «Дозволити» зберігається для підписаних програм. Для **непідписаного** `.app` система може питати знову при
  кожному запуску хоста; обхід — `socketfilterfw --add/--unblockapp <app>` з правами адміністратора (запит пароля
  через `osascript … with administrator privileges`). У плані це кнопка «Дозволити назавжди» з попередженням;
  рекомендація за замовчуванням — робити хостом Windows-машину.
- **Дозвіл «Локальна мережа»** (macOS 14+): і станція, і хост на Mac надсилають UDP-broadcast і з'єднуються з
  LAN-адресами, на що система питає дозвіл «Локальна мережа». Для цього у `build/mac/Info.plist` додається
  `NSLocalNetworkUsageDescription`; без ключа запит може не з'явитися, і станція мовчки нічого не знайде.
  Відмова виправляється лише користувачем (Системні налаштування → Конфіденційність → Локальна мережа) — програма
  відкриває цю панель кнопкою.

### 8.3. Самоперевірка на станції при підключенні

| Перевірка | Як | Що пропонує |
|---|---|---|
| Дозвіл «Локальна мережа» (macOS) | broadcast не отримав жодної відповіді і `/ping` до введеної адреси теж падає з `EHOSTUNREACH`/`EPERM` | Відкрити панель «Локальна мережа» з поясненням |
| Хост видно у мережі | broadcast відповів | Якщо ні — поле коду підключення + підказки: «обидва комп'ютери в одній Wi-Fi?», «спробуйте хот-спот з телефона» |
| TCP до хоста проходить | `/ping` без токена | Якщо broadcast відповів, а `/ping` ні → «на хості не пропускає брандмауер» з посиланням на §8.2 хоста |
| Версії сумісні | `protocolVersion` хоста ≠ станції | Показати обидві версії програми; «оновіть програму» (Налаштування → Оновлення) |
| Плагіни збігаються | перелік увімкнених плагінів із `/pair` | Запропонувати увімкнути відсутні (якщо встановлені) або попередити, що відповідні дисципліни покажуться як «Потрібен плагін» |
| Годинники | різниця `serverTimeUtc` і локального > 2 с | Попередження (ручне введення часу фінішу/старту на станції піде за годинником станції) |
| Тип відмітки | `app.db` обох машин: SportIdent vs Sport Time | Попередження, якщо різні (впливає на парсер зчитки й місткість чіпа) |

Усі результати пишуться у лог дій, щоб підтримка могла розібрати «чому не підключилось».

### 8.4. Файлові операції через хост і локальні файли станції

- **Експорт `.opyx`** (`/files/archive`): хост копіює `event.db` через SQLite backup API
  (`SqliteConnection.BackupDatabase`) у temp і пакує копію з рештою папки — так архів консистентний навіть коли
  станції пишуть під час експорту (сьогоднішнє читання живого файла з `FileShare.ReadWrite` при активних
  станціях могло б дати базу з застарілим WAL). Те саме й локально.
- **Імпорт `.opyx` на хост** (`/files/import`), архівування імпортованих XML у `events/<id>/day{N}` — на хості
  через `IEventFiles`/`RemoteArchiveService`.
- **Операції, небезпечні при підключених станціях**: зміна ідентифікатора змагання (`RenameIdentifierAsync` —
  `ReleaseAsync` + перейменування папки) і видалення змагання — хост блокує, якщо є активні станції на цьому
  змаганні, з переліком їх імен.
- **Локальні файли станції**: `views.json` під ключем `<hostId>/<identifier>`; лог дій у
  `<data root>/logs/<hostId>-<identifier>/` + `POST /log`; шляхи файлів зчитки (дефолт
  `<data root>/local/<hostId>/<identifier>/day{N}/event.csv`, `chips/rentchip.csv`) і збережений шлях сканування
  чіпів — у локальному `machine.json` тієї самої папки, а не в `ChipScanSettings` на хості; HTML монітора — у
  `<data root>/monitor/<identifier>/day{N}`.

логу дій на хості («[Mac-Реєстрація] змінено чіп учасника №12»).

3. **Тест діагностики**: `IStationDiagnostics` над підробленим мережевим станом (немає IPv4, зайнятий порт…) дає
   очікувані рекомендації.
4. **Тест ідемпотентності, перепідключення, jobs, перекладу ідентифікатор ↔ шлях** (відмова на `..`/роздільники).
5. **UI-тести**: сторінка «Спільна робота» в обох ролях (headless, скріншоти).
6. Документація: розділ у `CLAUDE.md` (межа мережі — `IEventStore`/`IEventFiles`/`IResultsAppData`/каталог/архів;
   нові методи повинні бути серіалізовними й класифікованими у `NotifyingEventStore`), `docs/network-protocol.md`
   (§4 розгорнуто), довідка у застосунку (`Help.Network.*`).
7. Реліз як мінорна версія (Windows + macOS); у нотатках — покрокова інструкція на одну сторінку.

## 10. Оцінка та ризики

| | |
|---|---|
| Обсяг | ~14–18 робочих днів разом із тестами й документацією; робочий прототип (етапи 1–2) — на 6-й день |
| Розмір збірки | +~30 МБ (ASP.NET Core runtime у self-contained пакеті) |
| Головний ризик | Мережа на місці: гостьовий Wi-Fi з ізоляцією клієнтів, «Публічний» профіль у Windows, дозвіл «Локальна мережа» на macOS. Відповідь — діагностика з §8 і рекомендація за замовчуванням: **хот-спот із телефона або кабель між ноутбуками** |
| Другий ризик | Дрейф `IEventStore`: новий метод із несеріалізовним параметром або без класифікації у `NotifyingEventStore` зламає станцію. Відповідь — контрактні тести (§9.2) падають на збірці |
| Що не вирішується | Робота станції без зв'язку (лише перегляд); конфлікт одночасного редагування однієї клітинки (виграє останній, як і зараз) |

## 11. Порядок впровадження

Етапи 1→2 дають перевірку ідеї на реальних двох машинах (Windows-хост, Mac-станція) і мають бути показані
користувачу до початку етапу 3; етапи 3 і 4 можна виконувати паралельно; етап 5 завершальний.
